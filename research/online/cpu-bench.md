# オンライン試作1：Node の戦闘 CPU 測定

Issue [#212](https://github.com/chevi0t/core-breaker/issues/212)。測定日：2026-11-07 UTC。
対象本体：`bfd0787`（Ver178）。実装・測定は `codex/212-node-sim-bench`。
通信なし、mesa、全員 BOT、各兵装の初期装備。将来の人間2〜4人＋BOT・計10機に向けた予備測定。

**結果：10機は1コアの28.0%、20機は49.1%。各11分・2試合の完走を確認した。**
ただし1刻みのp99は60.2ms / 88.6msで、滑らかな60Hzの処理期限は満たせていない。
小型VPSはまず1部屋で試す余地があるが、月3000円以内での品質・部屋数は候補機の測定前には確定しない。

## 実装と計測範囲

`server/headless.js` は本体スクリプトを読み込む Node VM アダプター。
three.js r128 と本体のマップ・武器・パーツ・パイロットの表をそのまま使う。
本体ファイルは変更せず、VM に渡す文字列だけに以下を適用する。

- `gameFrame` の可変刻みを 1/60 秒にする。
- `setup` の1番機も BOT にし、`selectedTeamSize` を5または10にする。
- `equip` の武器抽選だけを各兵装の初期装備へ固定する。機体パーツと戦闘の乱数は本体どおり。
- 描画・音・HUD の入口は無処理。全一覧は JSON の `muted` とアダプターの `NOOPS` に記録。
- `tracer` / `laserTrail` は視覚用到達時間0を返す。即着判定・ダメージは元から同期実行。
- `fire` / `shoot` / `blast` / `spawn` に観測用カウンターを追加する。

**銃口・当たり形状：** `muzzle`、`weaponLook`、`mechPose`、Mesh・boundingBox・Raycaster を残す。
各コマの戦闘→姿勢更新の順序を維持し、最後に `scene.updateMatrixWorld(true)` を呼ぶ。
この方法は形状・材質・一部の視覚状態の維持費も含む。最適化した純粋シミュレーションの下限値ではない。
全員 BOT のため `playerUpdate` のカメラ照準経路は未検証。人間のネット入力をそのままつなげられる状態ではない。

**時刻：** Node `performance.now()` の単調時計で60Hzをスケジュールする。
遅延時は刻みを飛ばさず追いつく。BOT の横移動など本体の `performance.now()` 参照も Node の壁時計を使う。
待機なしの `--fast` ではここが実時間測定と変わるので、容量推定には使わない。

**試合：** 元の `gameFrame` 内のコア・プラント・再出撃・勝敗判定を使う。
終了後は `setup()` で同じマップに再出撃し、計測プロセスを止めず次の試合を回す。
最初の読み込み・マップ作成は計測外、2試合目以降の再準備はCPU・実時間・イベントループ遅延に含む。
再準備は1刻みの処理時間には含まない。

**指標：** 1刻みは `gameFrame` と行列更新の実経過時間。
CPU は `process.cpuUsage()` の user+system を実経過時間で割ったもの（100%=1コア）。
GC の並列処理や観測処理も含む。RSS は毎秒サンプルの最大値なので瞬間ピークの厳密な上限ではない。
`monitorEventLoopDelay({resolution:10})` の値には約10msの測定間隔自体が含まれる。
これは入力RTTや時計の締切超過量そのものではない。
GC回数・時間は PerformanceObserver による累積値で、総停止時間との厳密な同値は仮定しない。

## ブラウザとの比較

`server/browser_compare.js` で既存の `bot_battle.js` を実行。mesa、同人数、全員BOT、各兵装の初期装備。
ブラウザは既存dbgの固定20Hz、Nodeは60Hz。ブラウザ側も描画の代わりに行列更新する既存試験で、GPU描画性能の比較ではない。
機体パーツ・戦闘乱数・演出による乱数消費・壁時計・最初の1機の再出撃には差がある。

| 10機 Node #2 | 300 | 86 | 17.2 | 92 | 4408 / 3681 | 時間切れ |
| 10機 ブラウザ #1 | 211 | 56 | 15.9 | 59 | 0 / 4751 | コア破壊 |
| 10機 ブラウザ #2 | 261 | 83 | 19.1 | 84 | 0 / 933 | コア破壊 |

撃破・死亡は両方とも最終スコアの合計。ブラウザログ先頭の「撃破」は死亡遷移の観測値で意味が違うため、表には使わない。
ブラウザの秒・コアは既存試験が整数に丸める。最初のコア耐久は両軍9000。

**20機は撃破ペース・コア残量が近い。10機はコアの減少と終了時刻に差が残る。**
10機のブラウザは2回ともコア破壊、Nodeは2回とも時間切れだった。撃破/分は近い範囲だが、
これを戦闘挙動が同等という合格判定にはしない。少数試行であり、刻み・乱数・演出無処理化のどの差が原因かは未切り分け。
固定60Hzを本体へ入れる前に、同じ機体構成と乱数条件で20Hz/60Hzおよびブラウザ/Nodeを比較する必要がある。
本Issueでは要求された比較結果と未解決点を残し、ゲームの数値やBotの挙動を合わせる変更は行わない。

ログ：[10機1回目](results/browser-10.log)、[10機2回目](results/browser-10-repeat.log)、[20機](results/browser-20.log)。すべてブラウザエラーなし、正常終了。

Nodeの完走試合では `ar` 発射が10機で1892/2209回、20機で2312/2243回、`rocket` 発射が10機で10/9回、20機で57/37回。
`blast` は各試合165〜300回、`spawn` は98〜209回。ロケット以外の爆発も `blast` に含む。
全機体の耐久・座標の有限性と機体数を毎秒確認し、例外なく完走した。

## 2 vCPU の部屋数概算

**試作は1部屋から。平均CPUの算術では10機で4部屋、20機で2部屋だが、運用品質を満たす部屋数は未確定。**

仮定：この環境と同等の1 vCPU性能、2 vCPUを持続利用可能、1部屋=1 Nodeプロセス、CPUの30%をOS・通信・変動用に残す。
最も重かった1分区間は10機31.7%・20機52.8%。`floor(2 × 0.7 / 使用コア数)` から、それぞれ4部屋・2部屋となる。
単一Nodeイベントループに全部の部屋を入れて2コアを使えるとは仮定しない。この試験は複数部屋同時実行の実測ではない。

この値は通信・履歴などを加える前のCPU計算上の目安。長いコマの問題があるため、この部屋数を推奨台数や提供保証には使わない。
候補VPSでまず1部屋を測り、長いコマを改善してから同時部屋数を増やす。

バースト制限の例として「各vCPUの持続基準20%」なら2 vCPU合計でも0.4コア分。
20機の平均0.491コアは既に超過。10機の平均0.280コアは収まるが、30%の余裕を残す0.28コア枠とほぼ同じで、重い区間0.317コアは超過する。
したがって「2 vCPU」という表示だけでは1部屋さえ保証できない。バースト枯渇後の持続性能を候補機で測る必要がある。
価格はこのIssueの範囲外で、月3000円以内に収まるかは未確定。

## 未検証・判断の限界

- 対象VPS、CPUバースト枯渇後、6時間・24時間の運用は未測定。今回の11分で持続保証はできない。
- WSS、暗号化、シリアライズ、履歴、入力検証、予測、再接続の負荷は入っていない。
- 人間プレイヤー、全装備、多マップ、複数部屋の同時負荷は未検証。
- 乱数は固定しない。ブラウザとの比較は分布を保証する統計試験ではなく、挙動の大まかな確認。
- 固定60Hzと描画無処理化は乱数の消費・呼出頻度を変える。戦闘結果の差をネット対応のバグと即断しない。
- 平均CPUに余裕があっても、p99の遅いコマや再出撃の同期処理は操作遅延になり得る。
  実用化前に長いコマの内訳を計測し、候補VPSで同じ試験と複数部屋試験を行う必要がある。
