# ブラウザホスト型オンライン試作（#212）

## 範囲

ホストのブラウザで現在のゲームを動かし、ゲストは PeerJS 1.5.5 の DataConnection で入力を送り、確定状態を表示する。強襲・重火力の初期装備。部屋は人間2〜4人、1チーム2〜10機（空席はBot）、通常コア戦の10マップとランダムから選ぶ。初期検証はmesa・計10機。時間刻みは既存の可変 dt。自機移動予測を追加した。ゲストの手持ちhitscanに最大200msのラグ補償を追加した。TURN・途中参加・ホスト移譲はない。main には入れず draft PR で確認する。

旧 `codex/212-node-sim-bench` は利用していない。Nodeの無描画CPU値はこの試作へ転用しない。

## 動かし方

```sh
npm install
npx playwright install chromium
python3 -m http.server 8000 --directory prototype
```

ブラウザで `http://localhost:8000/` を開き「オンライン（試作）」からホストが部屋作成、ゲストは部屋IDを入力する。通常は公開PeerServerで接続を仲立ちし、STUNだけを使う。音声・映像は接続しない。外部CDNで固定版PeerJSを読み込む。PeerJS/PeerServerはMITライセンスのソフトウェア依存であり、ゲーム素材ではない。

実試験は次の通り。ローカルPeerServerを自動起動し、固定版のnpm PeerJSを配信する。

```sh
node tools/test/online_transport.test.js
node tools/test/online_check.js dbg /tmp/online-check
node tools/test/online_bench.js dbg /tmp/online-bench
```

`online_bench` は既定で各300秒＋準備30秒。`--seconds=30 --warmup=5` は予備計測のみ。既存libのSwiftShaderを使う環境では実GPU/ユーザーPCの性能とは扱わない。

## 3つの判定と変更箇所

| 判定 | 意味 | 主な変更箇所 |
|---|---|---|
| `isHumanControlled(u)` | 人間から操作される機体 | 経路のBot条件、ジップ離脱、pitch、エリア移動、受け身、行動不能待ち、再出撃、装備、Bot役割、半自動/三点射、反動、近接対象、指示対象、機体更新 |
| `isLocalView(u)` | この画面の自機 | 命中/被弾/破壊/撃破/蘇生通知、カメラ・キルカメラ、ロック解除、スコア、ミニマップ、表彰、警告、武器UI、描画距離、チュートリアル/射撃場 |
| `isSimulationAuthority()` | 試合を計算するホスト/オフライン | gameFrameの試合進行全体、updateHumanUnit、ゲストの直接武器切替を要求へ変換 |

旧isPlayerは従来試験との互換と外部表示のため残す。controller未設定のオフライン機は旧判定にfallbackする。

`collectLocalInput` が入力を採取し、`updateHumanUnit` が共通の操作を行う。グローバルplayer/keys/cameraを遠隔機のたびに入れ替えない。遠隔機は `controlInput`、限定装備は `controlLoadout`。ゲストの視点と自機移動は即座に予測し、射撃・命中・施設はホスト待ち。他機は写真の到着間隔と揺れに合わせて60〜200msの範囲で補間待ち時間を徐々に調整する。写真が途切れた時の外挿は100msで止める。自機の先読みと確定状態への照合は下記②を参照。

## 状態と出来事

量子化した共通基準からの差分を最大20Hzで送る。位置・速度はcm精度、角度はミリラジアンの整数。不変値は初期または変更時のみ。開始条件はcontrolのprepareへ、初期基準と差分は写真専用線へ分け、復元できてからreadyを返す。正常時は初期情報を重複送信せず、欠落時は基準を再要求する。約10秒ごと/構造変更時に基準を更新する。各差分は直前の差分に依存せず、送信待ちの集約でも復元できる。未知の基準は再要求する。終了結果は写真に依存せずcontrolのmatchEndedで確定する。機体、装備、飛翔弾、コア、プラント、施設、残り時間、スコア、適用済み入力番号を含む。発射・射線・命中・爆発・音の出来事はコマごとに送る。ゲストでは自機移動の予測以外の物理、Bot、武器更新、弾道/爆風ダメージ、補給、施設判断、占拠、スコア/勝敗計算を止める。guest側は自機の未確定移動を除きホストの確定値を表示する。

入力保持は最新値、押下操作は未適用分をホストで一度消費。入力番号の重複・逆転、非有限値、許可外装備/出撃地点を拒否する。appVersionと通信規格が違えば理由を表示して入室を拒否する。

PeerJSの2接続/ゲストを使用。入室/承認/一度きり操作/出来事/開始/最終結果は信頼性あり・順序ありのcontrol、snapshot・snapshotBaseと連続inputBatchはordered:false・maxRetransmits:0の非再送線へ載せる。承認されたcontrol接続と写真接続を紐付け、両方の準備完了前に試合を始めない。送信バッファを監視し、未送信snapshotは最新へまとめる。送信量はJSONのUTF-8バイト数で、WebRTCの再送・暗号化・ヘッダーを含まない。

## 切断と制約

- 入力が250msない場合は保持入力を解除。3秒ない場合または接続が閉じた場合、HP・位置・装備を保ったままBotへ引き継ぐ。しゃがみなど人間の保持入力とロック対象だけは解除する。入力途絶でも通信が生きている場合、対象ゲストへ理由付き終了を通知し、その接続だけを閉じる。他のゲストは継続する。
- ホスト離脱、5秒の状態途絶でゲストは中断。ホスト移譲なし。
- シグナリングだけの切断では、確立済み対戦接続を閉じない。
- ホストのタブが裏に回るとブラウザが処理を抑制し、試合が止まる/中断する。前面で使用する。
- STUNのみなので直接接続できない回線の組み合わせがある。公開PeerServerの利用も不要になるわけではない。
- 知り合い用の試作。ホストの不正、照準自動化、秘匿情報の完全防御は対象外。

## 計測の区別

実WebRTCと異なる通信代替による機能試験を混同しない。

`--mock-transport` は試験コードだけがPeerJSをBroadcastChannelの代替へ差し替える。実WebRTC接続ができない環境で入力/状態/勝敗/切断ロジックを検査するためで、WebRTCの成立、NAT越え、本番通信性能を証明しない。結果JSONとログにもこの区別を書く。

入力遅延は同一ゲスト時計で入力採取から自機位置を描画したコマまで（予測ON/OFFを明記し、ONは未確定移動の反応）。射撃遅延は入力から標的HP/命中表示まで。人工遅延50/100msは送信側で1回ずつ追加し、両端で同じ設定にする。実ディスプレイの発光までの計測ではない。人間の実機試遊は別途必要。

20人時の送信量概算は、20機状態を使った1接続あたりの量を19倍する。10機の1/3接続だけを19/3倍してはいけない。19接続でのCPU・回線・ICE成立は未確認として区別する。

## 再試験を分ける指定

- `online_check.js ... --connections-only`：版不一致・途中参加拒否・通常切断・入力だけ途絶・ホスト終了を再試験。既定では2/4人の試合完走と武器も試す。
- `online_bench.js ... --load-only` / `--latency-only`：負荷と遅延を別々に実行。`--team-size=5|10`、`--guests=1|3`、`--latency-ms=0|50|100` で条件を絞れる。
- 低FPS時の観測送信量を20Hz設計の帯域と混同しない。20機のsnapshotサイズを記録し、20人用の所有者・ack欄を補ったサイズ×20Hz×19接続をsnapshot-onlyの概算として別記する。イベント、暗号化、再送、ヘッダー、19接続のCPU負荷はこの式には含まない。

## ロビーと開始・終了（2026-11-08）

ゲストの申請はホストが自動で許可する（#215）。満員・試合中・版違いは断る。接続前は初期状態・ロビー詳細・差分・試合情報を送らない。ホストはロビーで参加者を退出させられる。申告名は本人確認ではない。

部屋作成時とロビーで人数・マップ・チーム方式を設定する。ランダム方式では参加者を1行、希望方式では所属グループごとの2行に表示し、行をクリックして所属を選ぶ。満員の陣営へ移動できず、既存の参加人数/所属より小さな設定へ勝手に縮めない。シャッフルはホストのみ。ランダム所属はシャッフル/開始時に再抽選し、希望方式は選んだ所属を維持する。ランダムマップは作成時/その設定への変更時に一度抽選し、選ばれたマップを全員へ共有する。別の人数設定や開始で再抽選しない。自軍はどちらの所属でも青、敵は橙として表示する。

通信規格はv8（appVersion179）。旧v7以前とは理由付きで接続を拒否する。全ゲスト準備後にホストが開始時刻を配り、時計差を補正して3/2/1を出す。試合終了時はオンライン窓を開かず結果・表彰を見せ、「オンラインへ戻る」で部屋を閉じてロビー操作へ戻る。終了/退出時は移動・ブーストを含むループ音を全停止する。

人数20人は未対応。20機はBot込みの上限であり、人間20人の接続可否・CPU負荷を確認した意味ではない。追加の検証状況と通信量はvalidation.md参照。

## 写真専用線と補間（次段階①）

PeerJS1.5.5はreliable:falseだけではmaxRetransmitsを指定しないため、写真接続を生成する同期処理の間だけcreateDataChannelを限定して包み、固有の写真labelにordered:false/maxRetransmits:0を渡した後finallyで元に戻す。受信側でも実設定を検査する。標準のcontrolは変更しない。

大きな基準は16KiB未満の断片に分割し、期限と容量上限付きで再結合する。基準と通常写真は別の番号系列にし、先着差分が必要とする遅着基準を捨てない。同じ基準の再同期では残っている断片を再利用できるが、別のroom/matchや内容は混ぜない。写真に依存せず最終コア・表彰スコアをcontrolの終了通知で確定する。

人工損失率snapshotDropRateは論理写真/基準を捨てる試験設定。実ネットワークの個別fragment/packet損失とは別に扱う。試験結果と未検証条件はvalidation.md参照。

連続欠落時は描画時刻そのものも最新写真+100msで停止し、復旧後は最大1.2倍速で追いつく。停止中に名目時計だけが先へ進んで復旧時に大きく飛ぶことを避ける。60〜200msは目標バッファであり、欠落中の実遅延上限ではない。追加の復旧遅れと最小到着時刻差を基準にした表示遅れはrecoveryLagMs/effectiveDelayMsとして別に記録する（回線片道遅延込みの総遅延ではない）。再出撃/エリア移動の境界はlifeId/motionEpochで補間せず切り替える。

## 自機移動予測（次段階②、通信v6）

ゲストの連続入力は写真接続で最新5件を重ねて最大60Hz送信し、描画ごとの予測は送信間引きと分ける。押下・射撃保持状態はcontrolの独立actionSeqで管理する。番号/life/期限の検査により逆順・重複・前の再出撃の操作を除外する。

ホストと同じ移動処理を予測にも使い、実適用dtと入力ごとの累積dtをsnapshotで返す。ゲストは確定状態から未確定入力だけ再実行する。将来のhost dtは知り得ないため、未確定部分は仮dtであり誤差補正が必要。表示だけの補正はcamera描画中と機体モデルに限定し、照準や物理・送信値には入れない。

施設移動・近接・SPを消費する加速等は権威待ち。命中/ダメージ/弾数は予測しない。0.5m以上の誤差や再出撃/行動不能/装備・機体変更/予測履歴欠落は即時補正、その他は6描画frame以内で表示差だけ解消する。250ms入力途絶で中立化、500ms超の一度きり操作は失効（保持状態は押下なしで再同期）、3秒途絶はBot引継ぎ。

## ゲスト手持ちhitscanの巻戻し（次段階③、通信v7）

ホストは過去250msの機体の被弾形状（世界行列・骨・構成・生命/移動境界）を保持する。ゲストは最後に描き終わった写真時刻とanchorを入力へ付ける。まだ描いていない今frameの補間時刻とは分ける。ホストが測ったRTT、60〜200msの表示待ち、受信後の経過から時刻を検査し、最大200msに制限する。

手持ちhitscanの射線だけが一時的な過去の機体colliderを使う。射線の判定後、例外時も含めて現在の行列/被弾頂点/遅延更新キャッシュへ戻してから、既存damageを一度だけ適用する。HP・物理位置・障害物・バリアは過去へ戻さない。再出撃・転送・機体構成・死亡/蘇生の境界は跨がない。Bot自身の射撃、設置銃、背部自動砲、飛翔弾、近接は現在世界のまま。ゲストが撃つBot標的は巻戻し対象。

相手機のしゃがみ量とtiltは写真の表示時刻へ合わせ、二重に平滑化しない。骨アニメ位相の全量同期はせず、全ての見た目頂点と過去host形状が完全に一致するという保証はしない。標準の射線方向/散布を使い、ロックオンで照準の中心へ補正しない。

時計の方式上、host受信時に表示時刻は概ねRTT＋補間待ちだけ古い。片道100msでは200msの巻戻し上限を超え得るため、ラグ補償が有効でも表示通り全て当たる保証はない。未知anchor、非有限値、未来、古いlife、古い入力は安全に現在判定へ戻す。詳細の境界・比較値・未検証事項はvalidation.mdへ記録する。

## ゲスト別の秘匿と更新頻度（次段階④、通信v8）

全体写真を送ってから隠すのではなく、各ゲストへ公開できる機体とイベントだけを選び、個別の基準・差分を作る。名簿の名前/所属/スコア、コア/プラント/時間は共有するが、他人の入力ackや非公開の精密位置は送らない。

迷彩は生存中の味方いずれかが既存noticedの距離式（8 + vis²×80m）を満たす場合だけ公開する。旧ミニマップの「索敵済み」だけで遠い迷彩を公開する例外は採用しない。通常敵は80m以内、味方の索敵、または遮蔽物のない視野内なら公開する。距離だけで画面端やスコープの敵を消さないため、視野判定には最大垂直FOV100°・32:9相当の広い範囲を用いる。実際のゲスト画面内だけを保証する判定ではなく、極端な横長画面は未検証。迷彩/設置物の秘匿条件をscopeで解除しない。

近距離・照準付近・こちらを狙う敵・lock対象・scope中を優先し、遠方は2〜4回に1回更新する。unitUpdatesのbitで「見えるが今回は更新しない」と「見えない」を分ける。不可視はモデル/HUD/ミニマップ/音/lock/射線の描画側候補から除外し、再発見はvisibilityEpochを変えて補間せず切り替える。全機の枠と順序は固定し、不可視はhidden印と位置/向き/速度/HP/装備/行動の中立値へ置換する。可視切替だけでは基準を作り直さず通常差分で送る。hidden枠は毎回中立値との差分を載せるため、最初のhide写真を失っても古い可視値が復元されない。送信待ちの旧写真は可視集合の変更時に破棄する。

設置物も開始時の許可兵装から導いた容量の固定枠を使い、空きと未発見の枠は同じ印だけにする。現在許可される強襲/重火力の初期装備は設置物を含まないため通常部屋の容量は0。将来許可兵装を増やす時は既存spec.max等から容量を導く。全武器を開放したり架空の予備枠は作らない。非0容量は有限の設置武器を許可する試験で確認する。容量外/許可外の設置物は送らず、個数はホストの診断だけに残す。既存の味方発見条件（地雷/遠隔爆弾30m、sensor50m、sentry60m等と遮蔽）をイベントにも適用する。発射元の内部情報を保持して、未発見設置物のtracer/効果音などから座標を漏らさない。遅延キューから実際に送る時にも再判定する。既に送信した情報、飛行中の情報、以前に見えた位置は取り消せない。ホスト自身は計算のため全状態を保持するので、ホスト改造への防御ではない。

低頻度機はそれぞれ最後に実際に描いた時刻を③へ渡す。ホストは当該peerへ送信完了した差分そのものと、機体別の更新/可視epoch/生命/移動境界から検証する。未送信・他peerの写真、同frameでも異なる差分、最新機体sample+100msを超える申告は採用しない。省略した機体時刻にも同じ境界を適用する。

未開始ロビーや未割当peerのresyncは写真を返さない。viewer/module欠落時に全公開へfallbackせず、開始拒否または写真生成拒否とする。通信v8同士のみ接続する。PR #215（自動入室/結果ボタン）をオーナーの追加依頼で統合した。④の固定枠・秘匿条件は維持する。

## 実回線テスト版と通信司令室

オンライン窓の「実回線で試す手順」に沿って、2台・別回線で試す。部屋IDは明示的なコピーボタンで共有できる。試験版は正式GitHub Pagesとは別サイトへ配信し、main/gh-pagesに試作を混ぜない。STUNのみである制約とホストの前面表示は引き続き必要。公開URLの配信成功と、2回線間でのWebRTC/NAT成立・人による操作感は別々に確認する。
