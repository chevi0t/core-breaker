# 自然な一段目から屋根へ上がる設計

2026-10-21。知識台帳 M28 の根拠と、ユーザーと合意した次回の設計方針。

## 方針

ユーザーの指摘：「建屋高さが波状になってたら不自然だけど一段目が自然に配置されてると嬉しい」。建物の用途や街並みに合う高さを保ち、地上から屋根へ上がるための一段目を周囲に配置する。

- 工場街：荷捌き場のコンテナ、低い作業棟、搬入口の庇。
- 住宅地：ガレージ、物置、建物に付属する低い屋根。
- 基地：資材置場のコンテナや低い倉庫。防衛・索敵・侵入経路への影響も別に確認する。

全棟に同じ踏み台を付けず、街区ごとに複数の登り口を設ける。物の用途と置き方から登れることが見て分かる形にする。庇を足場として使うなら見た目だけにせず、歩ける面と頭上の空間を実装する。

3〜4m程度の一段目を候補にし、そこから屋根への高さの差が通常ジャンプで余裕を持って届くようにする。この寸法は本作の設計案で、原作の施設寸法を参照した値ではない。敷地全体を階段状にする、建屋の高さを周期的に上下させる、といった配置は採用しない。

## ジャンプを上げた後の実測

ジャンプ初速は `17 * sqrt(1.6)`、重力は34。計算上の頂点は6.8mだが、実際の物理更新では時間刻みで値が変わる。

| 時間刻み | 通常ジャンプの頂点 | ジャンプ直後の空中ダッシュ1回を併用した頂点 |
|---|---:|---:|
| 1/120秒 | 6.711m | 9.818m |
| 1/60秒 | 6.621m | 9.782m |
| 0.05秒 | 6.272m | 9.243m |

1/60秒の平地の箱への着地は通常ジャンプで6.8mまで確認でき、7mは失敗した。0.05秒では6.5mまで成功し6.8mで失敗。空中ダッシュ1回の併用ではそれぞれ10m・9mまで成功し、10.3m・9.8mで失敗した。測った高さは離散的なので、これらを厳密な限界値とは扱わない。ダッシュの開始時刻や回数を変えた上限も調べていない。

現在の `RULES.md` 等にある「通常で約7.3m、空中ダッシュで約10.5mに乗れる」は、この条件で着地を保証できる目安ではない。通常の登り口は高さの差を5〜6m以下にする案を基本にし、限界付近の段差を必須経路にしない。

既存の実マップでも代表例を確認した（1/60秒）。

| マップ・対象 | 通常ジャンプ | 空中ダッシュ1回を併用 |
|---|---|---|
| 潮路搬送区の4.8m・6m住宅、6mコンテナ | 着地成功 | 着地成功 |
| 丘の市街地の6m住宅 | 着地成功 | 着地成功 |
| 丘の市街地の7m・8m住宅 | 試した接近で失敗 | 着地成功 |
| 港の倉庫街の5.2mコンテナ | 着地成功 | 着地成功 |
| 港の倉庫街の8m・10m倉庫 | 試した接近で失敗 | 着地成功 |
| 潮路搬送区の12mコンテナ | 試した接近で失敗 | 試した接近で失敗 |

建物の高さは足元からの差で評価する。箱は敷地の最も高い地面に合わせて上面が決まるため、データの高さと接近側からの高さの差は一致しないことがある。例えば5.2mコンテナの成功例では、開始地点から上面までの差は約5.57mだった。

## 測定条件と限界

- エンジンはコミット `544f38c`、マップは同版の `prototype/maps.js`。seedは20261021。元データとソースのハッシュは [measurements.json](measurements.json) に保存した。
- `make_dbg.py` の `__g.physics` と `__g.shortDash` を直接呼んだ。各マップを初期化したときのプレイヤー1構成で、敵・砲台との交戦や勝敗の評価はしていない（対戦0戦）。本体・既存地形・武器性能は変更していない。
- 頂点は平らな昇降設備試験場で障害物配列を測定中だけ空にし、ジャンプ1回で測定。空中ダッシュはジャンプの次フレームに1回だけ入力し、ジャンプ長押しはしなかった。
- 箱への着地は同じ平地に幅25m・奥行き20mの箱を測定中だけ置き、縁の手前1.31〜12mの8地点から接近した。十分に箱の上へ入ったら移動入力を止め、上面への着地を確認した。
- 実マップは元の地形・障害物のまま、各対象の四辺から開始距離1.31・3・5・8mを試した。障害物の中になる開始地点は除外し、いずれかで着地に成功した時点でその条件を終了した。全建物・全接近方法を網羅した検査ではない。
- 頂点・箱への着地・建物全体を跨ぐことは別の条件。既存の住宅には幅20〜30mの棟もある。滞空を使う場合も水平距離とブースト残量を別に確認する。

今回確認したのは既存ジャンプの到達性。自然な一段目を足す案は方針として採用し、地形への実装・Botが選ぶか・実戦での利用や生還・陣営間の公平さは未検証として残す。

## 次回の地形変更で確かめること

1. 建物の用途・地上の射線・通行幅を先に決め、街区内の登り口を選ぶ。
2. 地上→一段目→屋根→隣の屋根または地上への連続した動線を設計する。段差だけでなく助走・着地面の幅と奥行き・屋根間隔・頭上を確認する。
3. 通常ジャンプで使える経路と、空中ダッシュ・パッド・リフトを要する経路を区別する。両軍・軽量/重量機・低FPS相当の時間刻みで実走する。
4. Botが登り口を選び、屋根から目的地へ抜けることを実Botで調べる。徒歩用navの接続だけでジャンプ経路が成立したとはしない。
5. 屋根からの射線が補給点・再出撃・基地防衛へ与える影響を再検査し、変更前後の試合で利用と損耗を確認する（M06/M14/M20/M25）。
