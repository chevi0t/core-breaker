# レシピから作る多層地形の試作

ローカル試作。公開マップへの置換・マージ・配信は行っていない。山岳の「風裂山道」を主成果とし、採掘場・高架／地下は生成器の再利用を確かめる小さな例。既存の武器・機体・移動・被弾・入力設定は変更しない。

## 作り方と試し方

Node.js・Python 3・リポジトリのPlaywright/Chromiumを使う。AIは `tools/terrain_recipes/*.json` を編集し、任意JSや頂点列を書かない。

```sh
npm install
npx playwright install chromium
python3 tools/build_terrain_preview.py tools/terrain_recipes/mountain.json /tmp/terrain-preview --seed 19
cd /tmp/terrain-preview
python3 -m http.server 8000
```

`http://localhost:8000/game/` を開き、PCのマップ選択で「風裂山道」を選ぶ。出撃、WASD移動、マウス視点、既存のジャンプ・ブースト・射撃操作が使える。音・Three.js・出典を同梱。フォントだけはオンラインなら外部から読み込む。既存のモバイル都市マップ除外条件を維持しているため、この試作はPC向け。スマホ対応・実機性能を保証する配布ではない。

生成コマンドはレシピ検査→既存マップ形式検査→実ゲームの標本脱出検査→試遊ファイルとハッシュを書き出す。失敗すると停止し、成功を示す `validation.json` は作らない。検査用 `check-game/` は通常試遊には不要。公開用ビルダーのHTML整形関数を再利用するだけで、gh-pagesを操作しない。

マップをリポジトリの試作一覧へ登録する場合は次の順序。`maps.js` を手で編集しない。

```sh
node tools/terrain_recipe.js tools/terrain_recipes/mountain.json prototype/maps/kazan_pass.js 19
python3 tools/build_maps.py
```

## 入力仕様 version 1

座標の配列はレシピでは **[x,z,y]**。トンネル矩形は **[xmin,xmax,zmin,zmax]**。本体のVector3の[x,y,z]とは異なる。

| 項目 | 内容・制限 |
|---|---|
| version, id, name | 1、英小文字ID、オリジナル表示名 |
| half, grid, navStep | 内部正方形の半径120〜300m、格子4/5/10m、nav間隔は格子の2倍 |
| seed | 整数。丘の高さを±5%変える。経路配置自体は変えない |
| boundary | 4〜40頂点の単純な直交凹多角形。格子上、自己交差なし。最後と最初は自動で接続 |
| color, baseHeight | 地形色 #rrggbb、基準高 |
| hills | [中心x,中心z,高さ,半径]。最大40個、cos曲線の丘 |
| bases | B/R の [x,z,y]。現在の施設テンプレートは南北向きの対称基地を想定。付属レシピの配置から始める |
| routes | id, kind, width, points。ground は blend、deck は thickness。幅8〜40m、勾配上限0.65。経路点は外周から離す |
| tunnels | axis x/z、rect、floor、ceiling。格子沿いの直方体の貫通空間。高さ8m以上、最大8個 |
| plants | [ID,x,z,初期所有B/R/null]、3〜6個 |
| blocks | 任意。[x,z,幅,奥行,下面,上面] の建屋プリミティブ |

実装上の検査は `tools/terrain_recipe.js` の `validate` と `validateConnectivity`。上位の未知フィールドは拒否する。入力を無制限の地形表現とは扱わない。トンネルの重なり・曲線坑道・斜め掘削・回転建屋・一般CSGは未対応。これらが必要ならスキーマとコンパイラを拡張し、同じ本体形式へ出力する。施設のオフセットも現状は固定テンプレートで、任意基地・任意プラント配置の公平性を自動保証しない。

## 地形・衝突・経路の関係

既存 `city-layout-v1` の圧縮三角形と空間索引を再利用する。地下床をdem、岩盤天面・天井・壁・橋をbridへ分類する。`terrainH` は下層の地面を返し、`groundAt(x,z,y)` は現在の高さに応じて到達できる支持面を選ぶ。単層heightfieldの下に床を足すだけでは入口が塞がるため、入口側の地面も床高へ接続する。低所の地面を作る処理が屋根の外縁まで低く削らないよう区分する。

地形から支持面を列挙し、歩行の高さ差・頭上・外周との距離を調べてnavを生成する。基地・経路点・プラントが同じ到達成分に入らなければ生成を拒否。施設を加えた後のnavは本体が再検査する。`nav.heightAware` 指定時のみ、BOTの目標・節点到着・近道を高さ込みで判断し、同じXZの別の階へ到着した扱いにしない。従来マップはこの指定を持たず、従来動作を維持する。

`cityTerrain.boundary` はプレイ可能域の凹多角形。衝突、カメラ、施設候補、nav、ミニマップ、境界表示に使う。内部の索引・キャンバスは正方形でも、歩ける領域は正方形に限定されない。境界マスクと、岩盤内を貫く三次元の穴は別の仕組み。

## 確認したこと

- 山岳：軽量・重量×7経路×往復の28本を実物理で走行。谷・山腹・尾根は実BOTナビゲーション、坑道・屋根・橋上下は制御入力で確認。
- 同じXZで床2mと天面34mを選択、坑道天井14m（有効高12m）。跳躍時の天井衝突、弾の坑道通過／天井・側壁・橋での停止、カメラ、凹境界、施設スポーンを含め39項目合格。
- 山岳・採掘場・高架／地下×seed19/41/97の9ケース。同じ入力の出力一致、8つの不正入力拒否、実物理の坑道・屋根・橋往復計54本が合格。テストは各定義を実際に別マップとしてロードしている。
- 脱出：5m格子と入口・橋縁・境界角を標本検査。5,569床のうち5,536はnavへの歩行接続を確認。残る33候補は重量二脚・重量ホバーで66回とも退出。開始時ブースト0、特殊装備なし、通常ジャンプあり。連続空間すべての保証ではない。ユーザー希望により追加の網羅検査は行わない。
- 施設検査：両端ポッドは敵側の129/132標本から露出なし、リスポーン距離48〜49m、基地カタパルト4基の着地点誤差約0.3m。実行時nav 1,322節点・4,596リンクが接続。
- 通常BOT戦は新マップと既存city/wide/mesa/dockを最大150秒、全武器テスト、既存都市形式テストでブラウザ／検査エラーなし。dockは87秒で通常決着。全自然BOTがすべての副経路を自発的に使うことや、勝率の公平性は未検証。

再実行用：`terrain_recipe_schema_check.js`、`terrain_recipe_check.js`、`terrain_portability_check.js`、`terrain_escape_check.js`（いずれもtools/test）。前二つのブラウザ系引数は検査用dbgフォルダと結果フォルダ。portabilityはその間に生成JSONのフォルダを渡す。escapeの任意第3引数は検査対象の定義JSON。`make_dbg.py`で検査用HTMLを作る。詳しい実行例は配布物の `REVIEW.md`。

## 負荷の測定と限界

山岳の生成地形は10,580三角形。テクスチャ追加なし。既存の統合描画・索引を使用し、機体4メッシュ構成は変更しない。

同じChromium、960×540、seed977、20/50/100機で、変更前city／変更後city／山岳を順序反転で2回ずつ測定。AI・物理・姿勢・射線等を含むCPUループ60フレームと、停止中の描画＋gl.finishを8回採取した。rendererは **SwiftShader**。実GPUやスマホのFPS比較ではない。

| 機数 | 変更前city CPU中央値（2回） | 変更後city | 山岳 |
|---|---|---|---|
| 20 | 4.8 / 5.1ms | 3.8 / 4.4ms | 5.2 / 3.0ms |
| 50 | 14.9 / 9.5ms | 9.5 / 8.3ms | 7.8 / 9.3ms |
| 100 | 20.2 / 19.8ms | 18.2 / 25.9ms | 13.5 / 14.9ms |

100機の描画中央値は変更前26.9/46.3ms、変更後33.8/36.1ms、山岳30.5/38.7ms。ばらつきが大きく、同等性能や改善を断定しない。生データは配布物 `evidence/performance.json`。山岳とcityは地形が違うので、山岳の時間差をエンジン改善の証拠にしない。

## 今回証明できた範囲

山岳の上下通路と凹外周を実ゲームで使い、同じコンパイラを採掘場・高架／地下の小例へ適用できた。3例は経路の骨格を共有するため、任意テーマの独立した良マップを自動発明できたという意味ではない。丘のないurbanはseedを変えても幾何が変わらず、seedメタデータだけが変わる。

地形は意図的な簡易造形で、岩肌の仕上げ、遮蔽物の戦術配置、勝率調整、長期の詰まり観測、実スマホGPU性能は残る。第一・最終プラントの高さも非対称で、公平な完成マップとは位置付けない。スクリーンショットは見通しのため撮影時だけ霧距離・視野角を調整し、ゲーム本体の設定は変えていない。公式画像を参考に地形の関係を読み取ったが、画像・モデル・配置は配布物に取り込んでいない。
