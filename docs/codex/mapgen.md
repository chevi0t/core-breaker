# 非対称・複層型対戦マップ 完全自律生成ルーチン設計書

**対象：拠点制圧・敵コア攻撃を伴うロボット対戦ゲーム**

## 1. 最終目標

人間が地形、プラント配置、BOTの行動経路を個別に設計することなく、プレイ可能で戦術的多様性のある非対称3Dマップを継続的に生成する。

生成された1つの地形には、プラント配置や移動施設が異なる複数の戦場バリエーションを持たせる。

生成・検証・改良はすべて自動で実行し、合格したものだけをゲームに登録する。

**最重要原則**

- 地形とプラント配置を独立して生成する。
- 地形生成時点で、複数の戦場バリエーションが成立する可能性を確保する。
- プラント配置を変更するたびにBOTの戦術ルートを再生成する。
- BOTは固定経路だけでなく、戦況によって経路を変更する。
- 見た目よりも、移動・交戦・戦術・バランスの成立を優先する。
- 人間による個別調整を前提としない。
- 不合格でも無制限に再試行せず、設定した試行上限で終了する。
- 生成と検証は可能な限り乱数シードで再現可能にする。

## 2. 全体実行フロー

以下を一連のルーチンとして自動実行する。

1. 既存ゲームのルール・移動仕様・マップ構造を読み取る。
2. マップの戦術的な骨格をランダム生成する。
3. 骨格を3D地形へ変換する。
4. 地形の通行可能性・複層接続・射線を検査する。
5. 地形内のプラント・施設設置候補地点を抽出する。
6. 同じ地形から複数のプラント配置案を生成する。
7. 各配置案に対して移動施設・リスポーン位置を決定する。
8. 各配置案のBOT戦術ルートを生成する。
9. BOTを実際に走行させ、移動不能や経路不良を検査する。
10. CPU同士で自動対戦し、戦況と陣営間の優劣を測定する。
11. 不合格の原因を分類し、対応する段階へ戻って自動修正する。
12. 合格候補から戦術的に異なるバリエーションを選抜する。
13. 地形と複数の戦場バリエーションをセットで保存する。
14. ゲームのマップ選択・読み込み処理に登録する。

## 3. 地形生成ループ

### STEP 1：戦術構造の生成

地形の外観より先に、ベース間を結ぶ3次元の移動・戦闘構造を生成する。

生成対象は、主進軍路、迂回路、合流地点、交戦空間、高低差、階層間接続、侵入経路などとする。

左右対称性は要求しない。

ただし、両陣営に攻撃・防御・迂回の選択肢を確保し、単一の狭い通路がすべての戦術を支配する構造を原則として避ける。

戦術構造は毎回同じパターンにしない。高低差、ルート分岐、合流位置、交戦空間の分布などを変化させる。

この時点ではプラント位置を確定しない。

### STEP 2：3D地形への変換

生成した戦術構造を、実際に移動・戦闘できる3D空間へ変換する。

階層は高さ座標を含めて管理する。同じXY座標に存在する上下階を別々の移動領域として扱う。

階段、スロープ、ジャンプ、落下、リフト、カタパルトなどは、各移動方法に応じた接続条件を持たせる。

最初は簡単な床、壁、足場、遮蔽物によるグレーボックス地形で構わない。

### STEP 3：地形の一次検査

次の条件を検査する。

- 両ベース間で移動可能な経路が成立している。
- 主要領域が移動経路ネットワークから孤立していない。
- 複層間の接続が実際の機体移動仕様と一致している。
- 機体の寸法や旋回、ジャンプ、ブーストを考慮して通行できる。
- 行き止まり・閉じ込め・意図しない落下が発生しない。
- 主要な攻撃経路と対抗・迂回経路が成立する。
- ベース付近で防御行動が成立する。

経路探索上の接続だけで合格とせず、必要な経路については機体の実走行で確認する。

不合格の場合、原因箇所を局所修正して再検査する。局所修正で解決できない場合は地形生成からやり直す。

## 4. 戦場バリエーション生成ループ

地形の一次検査に合格したら、**3D地形は固定したまま**以下を繰り返す。

### STEP 4：施設設置候補地点の抽出

地形全体を解析し、プラント、リスポーン地点、カタパルト、その他施設の設置可能地点を抽出する。

候補地点は、床面積、傾斜、高さ、遮蔽物、進入方向、射線、移動時間、周辺経路の接続状況から評価する。

一部の地域だけに候補が集中しないよう、地形全域・複数階層から候補を取得する。

### STEP 5：プラント配置案の生成

抽出した候補地点を組み合わせ、複数のプラント配置案を生成する。

プラント数、位置、占領順序、高低差、陣営からのアクセス経路を変化させる。

単なる位置の微調整ではなく、以下のように実際の戦い方が変わる配置を優先する。

- 中央の主戦場に戦力が集中する配置
- 左右の迂回経路が重要になる配置
- 高所と低所の確保が重要になる配置
- 複数方面への戦力分散が必要な配置
- 敵コアへの侵入と防衛の判断が重要になる配置

こうした類型を固定テンプレートとして強制するのではなく、生成結果の戦術的特徴として判定する。

続いて各配置に適したカタパルト、リスポーン地点、補給施設などを決定する。

### STEP 6：配置案の一次検査

各配置案について、両軍から各プラントへの到達時間、プラント間移動時間、敵コアまでの侵入時間、防衛側の迎撃時間、経路の独立性を評価する。

片方の陣営が明らかに不利となる構造、移動不能な目標、成立しない防衛経路を排除する。

ただし、すべての距離や移動時間を左右同一にする必要はない。高所優位、迂回性能、防衛性能など、異なる強みを持つ非対称構造を許容する。

不合格の場合は、まずプラントや施設の配置を変更する。地形そのものの変更は最後の手段とする。

## 5. BOTルーティング生成・検査ループ

### STEP 7：戦術ルートの自動生成

各プラント配置案について、両陣営それぞれのBOTルートを生成する。

最低限、次の戦術目的を対象とする。

- プラントへの進軍・占拠
- プラントの防衛・奪還
- 敵コアへの侵入
- 自軍コアの防衛
- 迂回・側面攻撃
- 味方への合流・支援
- 前線後退・再進軍

各目的に対して、可能な範囲で最速、安全、迂回など複数のルート候補を生成する。

ルートの評価には、移動所要時間、被攻撃リスク、高低差、射線、混雑、特殊移動の成功可能性を用いる。

移動性能が異なる機体には、それぞれ通行可能な経路を割り当てる。

### STEP 8：BOTの実走行検証

生成ルートに従って、実際のゲーム移動処理でBOTを走行させる。

確認事項は以下とする。

- 目的地まで到達できるか。
- 壁・段差・階段・上下階で停止しないか。
- カタパルトやジャンプの着地に成功するか。
- 同じ地点を往復して無限ループしないか。
- 複数BOTが密集して通行不能にならないか。
- 経路変更・目標変更後も正常に移動できるか。

不良が発生した場合、経路データ、移動制御、施設配置、地形のどこに原因があるかを分類する。

経路自体の不良なら再探索する。配置が原因なら配置案を修正する。地形が原因なら地形生成ループへ戻す。

### STEP 9：対戦中の動的経路判断

BOTは事前生成ルートだけに固定しない。

戦況、プラント占拠状況、味方の役割分担、敵の発見情報、危険地点、混雑などを反映し、戦術目標と使用ルートを更新する。

BOTが使用できる敵情報は、実際のゲームルールに即した索敵・視認・味方共有情報に限定する。評価用の完全な敵位置情報をBOTに直接渡さない。

事前生成ルートは基本候補として利用し、移動中に条件が変化すれば部分的に再探索する。

プラント配置を変更した場合は、経路候補、目的地、関連する特殊移動リンクを再構築する。

## 6. 自動対戦・評価ループ

### STEP 10：高速対戦検証

一次検査を通過した配置案について、BOT同士で自動対戦を実施する。

可能であれば描画を省いた高速実行とし、ゲーム本来の移動・戦闘・占領・勝敗ルールを維持する。

対戦では複数のBOT戦術を使用する。攻撃重視、防衛重視、拠点重視、迂回重視など、行動方針の違う構成を組み合わせる。

同じBOT構成を両陣営に入れ替え、同一条件に近い乱数設定で比較する。

**記録する指標**

- 陣営別勝率と統計的不確実性
- 初動プラント到達時間
- プラントの占領・奪還回数
- 各プラントの占領時間
- 敵コアへの到達回数・攻撃成功率
- 自軍コア防衛の成功率
- 各経路の利用人数・利用頻度
- BOTの移動失敗・停滞・経路変更回数
- 交戦地点の分布
- 各階層・各エリアの利用率
- 各BOT戦術に対する陣営有利度

少数試合で予備選別し、有望候補に対して試合数を増やす。

未実行の模擬戦や簡易経路モデルから得た推定値を、実対戦の計測値として扱ってはならない。

### STEP 11：バランス判定

通常の拠点制圧戦では、暫定目標を陣営勝率45～55％とする。

単なる観測勝率だけで合格にせず、試合数と信頼区間を確認する。初期案として、95％信頼区間が45～55％の範囲に収まることを統計的合格条件とする。

さらに、勝率が均衡していても、以下の場合は不合格候補とする。

- 両軍が膠着し、目標攻略がほとんど成立しない。
- BOTが特定経路だけを使い続ける。
- 一部の重要エリアが事実上使用されない。
- 一方の陣営だけが極端に守りにくい。
- 特定のBOT行動パターンへの過剰適合が見られる。
- 経路探索や移動制御の失敗が戦局を左右する。

最適化に使用していないBOT戦術構成でも検証し、特定BOT専用のマップになることを防ぐ。

### STEP 12：原因別の自動修正

不合格の場合、原因に応じて修正箇所を変える。

| 不合格原因 | 修正対象・戻り先 |
|---|---|
| 到達不能・地形の欠陥 | 地形生成・経路構築 |
| BOTの走行不能 | 経路・移動制御・接続設定 |
| 一方の初動が極端に有利 | プラント・移動施設配置 |
| コア侵入や防衛が成立しない | 施設配置・ベース周辺経路 |
| 特定経路にBOTが集中 | 経路コスト・戦術判断。地形も検査 |
| 勝率が大きく偏る | プラント・施設配置から順次修正 |
| どの配置でも膠着する | 地形の戦術構造 |
| BOTが共通して不合理な行動をする | BOTの行動ロジックを修正 |
| 戦場同士の戦い方が同じ | 配置案再生成。必要なら地形修正 |

修正後は、影響を受けた検証を必ず再実行する。

地形を変更した場合、既存プラント配置・経路・対戦結果の妥当性を再確認し、古い評価値をそのまま引き継がない。

## 7. 地形全体の合格判定ループ

### STEP 13：複数戦場の成立性を評価

個別の戦場バリエーションが合格しても、地形全体を直ちに合格させない。

同一地形から戦術的に異なる複数の合格バリエーションを確保できるか確認する。

初期目標は、**1地形につき3種類以上の合格バリエーション**とする。

戦場間の差異はプラント座標の違いだけで判断しない。

各バリエーションの主要交戦地点、経路利用分布、高所利用率、コア侵入方向、プラント間の戦力移動などを比較する。

これらがほぼ同じなら、別の戦場として数えない。

多様性が不足する場合、まず施設配置案を再生成する。それでも改善しなければ、分岐構造や交戦空間を変更した新しい地形を生成する。

**地形の合格条件は、「1つの良い戦場が作れること」ではなく「複数の異なる良い戦場を作れること」とする。**

## 8. 自動最適化の探索方針

単純にランダム生成を繰り返すだけでなく、優良候補を保持しながら改良する。

- 合格条件を満たさない候補は、原因に応じた局所修正を優先する。
- 改良しても品質が上がらない場合は、元の候補へ戻す。
- 成績上位の候補を保持し、その近傍の配置や構造を探索する。
- 同じ構造へ収束しないよう、新規性の高い候補も一定数保持する。
- 修正を繰り返しても改善しない場合は、新しい乱数シード・構造から再生成する。
- 勝率だけを最大化せず、接続性、移動信頼性、戦術多様性、陣営均衡を別々に評価する。

重大な通行不能や到達不能は、総合点が高くても不合格とする。

各反復には計算量・試行回数の上限を設定する。予算切れの場合は未合格として終了し、最良候補と不合格理由を保存する。

## 9. 初期運用パラメータ

以下を仮の初期設定とし、ゲーム仕様と実行性能に合わせて調整可能にする。固定値としてコードに埋め込まない。

| 項目 | 初期設定 |
|---|---|
| 生成対象 | 1地形 |
| 地形生成試行 | 最大30回 |
| 1地形の配置案生成 | 最大64案 |
| プラント数 | 3～6基 |
| 最低合格バリエーション | 3種類 |
| 主要目標への経路 | 原則2系統以上 |
| 走行検証 | 複数機体種・複数乱数条件 |
| BOT戦術 | 5種類以上を検討 |
| 予備対戦 | 候補当たり200試合を目安 |
| 最終対戦 | 有望候補当たり2,000試合以上を目安 |
| 勝率目標 | 45～55％ |
| 統計的判定 | 95％信頼区間を考慮 |

数値条件は暫定値であり、非対称性の許容度やゲームルールによって再校正する。

試合数が不足している場合は「勝率未確定」として扱う。

## 10. 合格後の保存・登録ルーチン

地形と戦場バリエーションを分離して保存する。

保存対象は以下のとおり。

- 共通3D地形データ
- 地形用の基本ナビゲーションデータ
- 施設設置候補地点
- バリエーションごとのプラント・施設配置
- バリエーションごとのBOT戦術ルートと特殊移動リンク
- 経路検証の結果
- 自動対戦の実測結果
- 陣営バランスの評価結果
- 戦場間の多様性評価結果
- 乱数シード、生成設定、ゲーム仕様バージョン
- 不合格履歴と自動修正履歴

ゲーム起動時には、共通地形を読み込み、選択された戦場バリエーションの施設配置とBOTルートを適用する。

新しいバリエーションの追加時は、地形を再生成せず、原則として配置生成以降の処理を実行する。

プラント数や戦場構成が異なる場合も、共通地形データを再利用する。

## 11. 実装・検証時の遵守事項

この設計書を既存ゲームへ実装する際は、最初にリポジトリ全体を調査し、ゲームエンジン、移動物理、既存マップ形式、BOTの行動ロジック、対戦ルールを把握すること。

既存実装を可能な限り利用し、同等機能の重複実装を避けること。

ルーチンは次の順序で段階的に動作確認する。

1. 地形を自動生成して保存・再読み込みできる。
2. 一つの地形に異なるプラント配置を自動生成できる。
3. 配置変更後にBOTルートが自動更新される。
4. BOTが地形を実走行し、移動失敗を自動検出できる。
5. BOT同士の対戦を自動実行して結果を収集できる。
6. 不合格に対する修正と再検証が自動実行される。
7. 戦術の異なる複数の合格戦場を保存・読み込みできる。
8. 以上を無人で連続実行できる。

各段階で自動テストを用意し、実行結果を確認してから次へ進む。

自動対戦環境が未実装の場合、勝率検証済みと偽って先に進めてはならない。

外部のLLMをマップ生成の各反復で呼び出すことは必須としない。生成器が手続き的に候補を作り、検証と修正を自動実行する方式を基本とする。

## 12. 最終受入条件

以下をすべて満たした場合に、完全自律生成ルーチンの初期完成とする。

- 人間によるマップの個別修正なしで生成を開始・終了できる。
- 非対称で複層構造を含む地形を生成できる。
- 一つの地形から3種類以上の戦術的に異なる戦場が成立する。
- 各配置に応じてBOTの戦術ルートが自動生成される。
- BOTが実際のゲーム移動処理で主要経路を走破できる。
- 戦況変化によるBOTの経路変更が機能する。
- 自動対戦による勝率・戦況評価が実行される。
- 不合格時に原因へ対応する修正と再検証が実行される。
- 合格した地形とバリエーションがゲームから読み込める。
- 同じ生成条件から再現可能な結果と検証履歴を取得できる。
- 指定予算内に合格候補がない場合は、失敗を明示して安全に終了する。

**最終的には、生成シードと設定を入力するだけで「新地形1つ＋戦術的に異なる複数の戦場＋各戦場のBOTルート＋検証結果」が自動的に完成する状態を目指す。**
