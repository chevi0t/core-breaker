# マップを作る手順（Codex など向け）

オーナーの指定（2026-10-19）：**テーマから Bot の動き（Bot のルール）まで、作る人が決めてよい**。名前・副題・大きさ・人数・試合時間・プラントの数と配置・地形・施設の置き場所・Bot の通り道と動き方を自分で決め、決めた理由を PR の説明と `mapdesign/<id>/README.md` に書く。

変えてはいけないのは、`prototype/maps/RULES.md` で「ユーザー指定」と書いた決まりだけ。主なもの：

- 名前はオリジナル。元のゲームのマップ名・地名・形はそのまま使わない（作りの考え方は借りてよい）。
- 一番自軍側・敵軍側のプラントのリペアポッドは、プラントの後ろ（自軍ベース側）の土手と窪地に隠し、敵陣側から見えないようにする。
- ベースのカタパルトは各ベースに左右2基ずつ。どの台も誰でも使える（敵も）。着地点の印は付けない。
- レーダーは各ベースの左奥。
- 道路・広場・住宅地は平らにする（`paved` に書いて `gen_rough.py` が起伏を置かないようにする）。
- Bot もプレイヤーと同じルールで動く（Bot だけが通れる道や、Bot だけが見える物は作らない）。

## 自動生成の設計書との合わせ方（オーナーの指定 2026-10-19）

オーナーはマップ作製のルールとして `docs/codex/mapgen.md`（非対称・複層型対戦マップ 完全自律生成ルーチン設計書）を渡した。マップはこの設計書のルーチンで作る。この手順書は、今のエンジンでのマップの書き方と確かめ方として使う。今の作りとぶつかる所は次のように扱う。

| 所 | 今の作り | 設計書に合わせて |
|---|---|---|
| 点対称 | 自軍側の半分を書くと、エンジンが敵軍側を点対称に足す（`featuresOf`・`mirrored`、`nav` の `~番号`、`mirrorPlant`、カタパルト） | 非対称でよい。両側を書けるマップの項目（例 `asym: true`）をエンジンに足してよい。その項目が無い今の4マップは今のまま |
| 複層 | 地面は高さの地形（`terrain`）、上に乗れる箱（`layout`）、下をくぐれる橋（`bridges`）。通り道の節点は高さ y を持てる | 上下階はまずこの組み合わせで作る。足りない物（屋内の階、リフトなど）はエンジンに足してよい（今のマップの動きは変えない） |
| 対戦の数 | `bot_battle.js` はブラウザで描画しながら動かすので、1試合に数分かかる | 200〜2000試合には、描画を省いた速い対戦の仕組みが要る。移動・戦闘・占拠・勝敗の決まりを変えずに作る。できるまで、または試合数が足りないうちは「勝率未確定」と書く（設計書 §9・§11） |
| Bot | `botUpdate` の役（`BOT_ROLE`）と通り道 `nav` | 経路の作り直しや、戦況による目標と経路の切り替えを足してよい。敵の情報は今と同じく、見えた物・索敵・レーダーだけ（AGENTS.md の5）。新しい項目が無い今のマップの動きは変えない |
| 戦場の違い | 配置違いは `variants`（メニューに「名前 〜副題〜」で並ぶ） | 1つの地形の3つ以上の戦場は `variants` で入れる（設計書 §11「既存実装を可能な限り利用」） |
| ユーザー指定の決まり | `RULES.md` と上の一覧 | 自動生成のマップにも守らせ、生成器の検査に入れる（隠したポッドが敵陣側から見えない、再出撃はプラントの中心から46〜52m、ベースのカタパルトで中央のプラントへ直行しない、道路・広場は平ら、など）。点対称だけは外してよい |
| 登録と公開 | `maps/<id>.js` → `build_maps.py` → `maps.js`。公開ページへの反映はマップ製作のスレッド | 生成器の出力も `prototype/maps/<id>.js` にし、`build_maps.py` と `map_check.js` を通す。シード・設定・検証の記録（設計書 §10）は `mapdesign/<id>/` に置く。公開は今の流れのまま |
| PR | 1マップ1つ | 設計書 §11 の段階（1〜8）ごとに分けてよい。各 PR に段階の番号と、自動テストとその結果を書く |

## 0. 読む物

0. `docs/codex/mapgen.md`（オーナーの設計書）と、上の「自動生成の設計書との合わせ方」。
1. `prototype/maps/README.md`：ファイルの形、地形の種類、橋・水面・建物・通り道・配置違い、確かめ方、今あるマップの説明。
2. `prototype/maps/RULES.md` の第2章以降：大きさの目安、ベース・プラント・ポッド・カタパルトの決まり。第1章の流れのうち「頼む」「公開する」「配る」は Claude がする。
3. 今あるマップのうち一番近い物を1つ読む。5対5なら `mesa.js`、10対10なら `wide.js`、建物・橋・川・通り道の見本は `city.js`、コスト制の小さいマップは `dock.js`。
4. `mapdesign/LESSONS.md`：過去の設計で外れた仮説・実測の根拠・次回の検査。今回関係する知識IDを設計メモに引用し、試作後に採用/棄却と新しく分かったことを追記する。

## 1. 決める（企画）

`mapdesign/<id>/README.md` に次を書いてから座標を書き始める。

- テーマ、名前（と副題）、`<id>`（英小文字・数字・_）
- 人数と時間：5対5なら5分、10対10なら10分が今の目安（変えるなら理由を書く）
- 大きさ：5対5で 270m×480m、10対10で 360m×600m 前後が目安
- プラントの数と、最初の持ち主（自軍側・中立・敵軍側）
- 戦いの流れ：主な通り道（2〜3本）、回り道、高台、狭い所（激戦になる所）、身を隠せる物の置き方
- ベースの施設：コアの位置（`baseZ`）、境目（`baseLine`）、防衛砲台、リペアポッド、カタパルトの台と着地点
- Bot の動き：下の「6. Bot のルール」

## 2. 座標の決まり

- 単位は m、y が高さ。自軍（青）は +z 側、敵軍（橙）は -z 側。自軍から敵ベースを見て左が -x。
- `terrain`・`layout`・`turrets`・`radar`・`catapults`・`basePods`・`barricades`・`bridges` は**自軍側の半分だけ**書く。敵軍側は原点をはさんだ点対称の位置に自動で足される。
- `plants` と `plantPods` は全部書く（点対称にしない）。自軍ベースに近い順に並べる。
- 施設・ポッド・カタパルトは置いた所の地面に乗る（高さは書かない）。
- 登れない斜面は傾き1.1（約48°）より急な所。ジャンプは約6.8m（2026-10-20から）。平地から乗れる箱の高さは、ジャンプだけで6.5〜6.8m、ジャンプ直後の空中ダッシュ込みで9〜10m（FPSで変わる）。登り口の段差は5〜6m以下、越えさせない壁・崖は11m以上。屋根へは建物の高さを波状にせず、物置・ガレージ・コンテナ・庇などの自然な一段目（3〜4m）から上がる（ユーザー、2026-10-21。prototype/maps/RULES.md §5）。

## 3. ファイルを書く順

`prototype/maps/<id>.js` に、この順で足していくと確かめやすい。

1. `order`・`name`・`size`・`team`・`time`・`baseZ`・`baseLine`・`desc`
2. `terrain`：大きな地形（`block` の高台、`trench` の谷、`ramp` の坂、`mesa`）。最後に「// 起伏ここから」「// 起伏ここまで」の2行だけを置いておく（中は 4. で作る）
3. `layout`：建物・壁・資材など（`[x, z, 幅, 奥行き, 高さ, 見た目]`）
4. `plants` → `plantPods`（一番手前のプラントのポッドは隠す）
5. `turrets`・`radar`・`basePods`・`catapults`・`barricades`
6. `bridges`・`water`（あれば）
7. `nav`（6. Bot のルール）
8. `paved`：道路・広場・家の並ぶ所の長方形 `[x0, x1, z0, z1]`（自軍側の半分。エンジンは読まない、起伏の道具だけが使う）

ここまでで一度 5. の確かめ方を回し、上から見た図で形を直してから細部に進む。

## 4. 起伏を付ける

```sh
python3 tools/gen_rough.py <id>        # terrain の「起伏ここから」〜「起伏ここまで」の中を作り直す（--seed N で別の並び）
```

`paved`、家と石壁の周り、プラントの占拠範囲、ポッド、カタパルトの台、橋、水面、もとの地形の上には置かない。地形を変えたら毎回作り直す（手で直さない）。

## 5. 組み立てて確かめる

```sh
python3 tools/build_maps.py                      # 必須項目、プラントIDのつながり、座標の範囲を調べて prototype/maps.js を作る
python3 mapdesign/map_top.py <id> mapdesign/<id>/top.png   # 上から見た図（高さ・登れない斜面・障害物・通り道・再出撃位置）
python3 tools/test/make_dbg.py dbg
node tools/test/map_check.js dbg <id>            # 全部（カタパルトとスクリーンショットつき）
node tools/test/map_check.js dbg <id> --quick    # 施設・ポッドの見え方・再出撃位置だけ
```

map_check の結果で★が付いた所は全部直す。合格の目安：

- 施設が地面に乗り、障害物に埋まっていない。
- 隠すポッドは、敵陣側から見える所が0か所。
- 各プラントからの再出撃位置が、中心から自軍ベース側へ46〜52m で、崖の上・障害物の中・川の中でない。
- カタパルトの着地点が、書いた所から6m以内。
- 通り道（`nav`）に★が無い。

## 6. Bot のルール

Bot はどのマップでも同じ考え方で動く（`index.html` の `botUpdate`）。

- 役：`BOT_ROLE` の順に、攻め（`attack`：敵コアの傘の下、コアの前12mへ）、プラント（`plant`：自軍のものでない一番近いプラントへ。プラントが4つ以上なら番号で1つ先にも分かれる）、守り（`defend`：レーダーに映ったベースの侵入者へ。いなければベースの前60m）。
- 支援は傷ついた味方のそばへ、耐久が35%を切ると一番近いポッドへ行く。
- 出撃位置は役で変わる（`botSpawn`：守り以外は6割で一番前のプラントから、ベースから出るときはカタパルトを使うことがある）。
- 目標までまっすぐ歩けないときだけ、`nav` の通り道をたどる（`navSteer`）。

このマップで Bot をうまく動かすには、まず `nav` で足りるかを試す。

- 節点は曲がり角、橋の両端、坂の上と下、プラントの手前、ベースの出口に置く。つなぐ2点の間は、障害物も登れない段差も無くまっすぐ歩けるようにする。
- 点対称の節点は `'~3'`（3番の点対称）で書く。原点には置かない（プラントの柱がある）。
- 迂回路にも節点を置かないと、Bot はそこを使わない。

`nav` だけでは足りないとき（例：高台を取りに行く役、決まった回り道を通る攻め役、このマップだけの出撃のしかた）は、マップに新しい項目を足し、`botUpdate`・`botSpawn` でそれを読む処理を書いてよい。そのときは：

- 項目は無くてもよい物にし、無いマップの動きを変えない（今のマップで `bot_battle.js` の結果が大きく変わらないこと）。
- プレイヤーと同じルールを守る（壁抜け、見えない敵への照準などはしない）。
- 項目の意味を `prototype/maps/README.md` の「ファイルの形」に書き、処理を `docs/DESIGN.md` の Bot の所に書く。

## 7. Bot 戦で確かめる

```sh
node tools/test/quick_check.js origin/main                 # 増えた・変わったマップと city で Bot 戦を60秒（武器・パーツの変更があればそれも試す）
node tools/test/bot_battle.js dbg <id> 150
node tools/test/bot_battle.js dbg city,wide,mesa,dock 150   # エンジンの Bot を変えたときは今のマップも
```

合格の目安：「エラー なし」、両軍に撃破がある、プラントの持ち主が試合中に変わる、Bot が同じ所で止まり続けない（必要なら `bot_battle.js` に表示を足してよい）。
