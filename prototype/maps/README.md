# マップの書き方（prototype/maps/）

コアブレイカーのマップは、このフォルダに1マップ1ファイルで置きます（v0.10.1でエンジンの index.html から分けた）。
エンジン（index.html）はマップの中身を知らず、`maps.js` に入っているマップをマップ選択に並べます。
設計の決まり（ユーザー指定と仮決めの区別つき）と作ってから公開するまでの流れは [RULES.md](RULES.md) にまとめてあります。

## 担当と流れ

- **このフォルダはマップ製作のスレッドが持つ**（ユーザーの希望でマップ製作を別の流れにした）。エンジン側（index.html、zip、効果音、BGM）は「ボーダーブレイクPC再現」スレッドが持つ。
- マップを足す・直す：
  1. `prototype/maps/<id>.js` を書く（下の「ファイルの形」）。
  2. `python3 tools/build_maps.py` で `prototype/maps.js` を作り直す（中身の確認つき。問題があれば書かずに止まる）。`maps.js` は生成物なので手で編集しない。
  3. 確かめる：`python3 tools/test/make_dbg.py 作業フォルダ` → `node tools/test/map_check.js 作業フォルダ <id>`（下の「確かめ方」）。
  4. 公開とzipは下の「公開」。
- エンジンの変更が要るとき（新しい地形の種類、11機以上の陣営、新しい施設など）は、エンジン側のスレッドに頼む。エンジン側がマップのファイルを直すときは、マップ製作のスレッドに頼む。

## ファイルの形

```js
// 説明のコメント
(window.MAP_DATA = window.MAP_DATA || {}).<id> = {
  order: 3,                 // マップ選択の並び順（小さいほど上）。無ければ最後
  name: '〇〇演習場',        // マップ選択に出る名前
  size: [180, 300],         // [x の半分, z の半分]（m）。マップは x ±size[0]、z ±size[1]
  team: 10,                 // 1陣営の機数（プレイヤーを含む。1〜10）
  time: 600,                // 試合の秒
  baseZ: 265,               // 自軍ベース（コア）の z。敵軍は -baseZ
  baseLine: 205,            // ベースの境目の z（レーダーの探知、スコアの侵入判定。ここから25mで地形が平らになる）
  desc: '…',                // マップ選択の説明（地形、ポッド、カタパルトの場所）
  terrain: [ … ],           // 地形の起伏（下の表）
  layout: [ … ],            // 障害物 [x, z, 幅, 奥行き, 高さ, 見た目]（見た目は 'house'・'wall'・'tower'、省くと灰色の箱）
  plants: [['A', -55, 150, 'B'], …], // プラント [ID, x, z, 最初の持ち主 'B'・'R'・null]。自軍ベースに近い順に書く
  turrets: [[-36, 215], …], // 防衛砲台 [x, z]
  radar: [-55, 275],        // レーダー [x, z]（ベースの左奥）
  catapults: [[-70, 240, -45, 40], [-35, 172, -14, 20, 'A'], …], // [台の x, z, 着地点の x, z, プラントID]。どの台も誰でも使える（v0.10.5）。IDはBotがそのプラントから出た時に使う台の目印
  basePods: [[-21, 238], …],          // ベースのリペアポッド [x, z]
  plantPods: [['A', -57.5, 180], …],  // プラントのリペアポッド [プラントID, x, z]
  barricades: [[-100, 205, 16, 2, 6], …], // 壊せる壁 [x, z, 幅, 奥行き, 高さ]（耐久30000）
  // ここから下は無くてもよい（v0.10.3から）
  subtitle: '中央決戦',      // 副題。マップ選択の名前が「名前 〜副題〜」になる
  bridges: [[60, 12, 56, 6, 14, 2], …], // 橋の板 [x, z, 幅, 奥行き, 上面の高さ（海抜）, 厚さ]
  water: [[-26, 98, 145, 12, -4.5]],    // 水面 [x, z, 横の半分, 奥行きの半分, 高さ]（見た目だけ）
  nav: { nodes: [[0, 222], …], links: [[0, 1], [13, '~12'], …] }, // Botの通り道
  variants: { key: { name: '高台争奪', plants: […], plantPods: […], catapults: […] } }, // 配置違い
  vs: { cost: 20000, death: 2000 }, // VS風のコスト制（両軍の戦力ゲージ、撃破1回で減る量）。v0.10.9 から。ある時はコア・傘・砲台・レーダーを作らない
};
```

- `<id>` はファイル名と同じ（英小文字・数字・_）。選んだマップは `localStorage` の `coreBreakerMap` に ID で残る。
- 座標の単位はm、y が高さ。自軍（B、青）は +z 側、敵軍（R、橙）は -z 側。`yaw = 0` で -z（敵ベース）を向く。
- **点対称**：`terrain`・`layout`・`turrets`・`radar`・`catapults`・`basePods`・`barricades` は自軍側の半分だけ書けば、敵軍側は中央 (0, 0) をはさんだ点対称の位置に自動で足される。x・z がともに0の地形と障害物は1つだけ置かれる。
- **プラントとプラントのポッドは全部書く**（点対称にしない）。プラントIDを付けたカタパルトは、敵軍側では点対称の位置にあるプラントの台になる。
- 施設・ポッド・カタパルトは置いた場所の地面（`terrainH`）に乗るので、高さは書かない。斜面に置いた障害物は低い側の地面まで埋まり、高い側の地面から「高さ」ぶん出る。
- マップの外周には壁が自動で付く。

### 非対称の生成マップ（`asym: true`）

`tools/generate_map.js` の出力は `asym: true` を持つ。この場合、`terrain`・`layout`・`bridges`・`water`・`barricades`・`nav` は**両陣営を含む全域**を書き、点対称に増やさない。nav の節点は高さを持てるが、`~番号` は使わない。プラントとプラントのポッドは従来どおり全部書く。ベースの `turrets`・`radar`・`basePods`・`catapults` には従来どおり自軍側を書き、両軍へ展開する。`asym` を省略した既存マップは従来と同じ。

生成地形は `--seed`、施設配置は `--placement-seed` で分離して再現する。起伏は `tools/gen_rough.py`、施設検査は `map_check.js` を使い、地形・配置・実走行の検査に通った開発候補を保存する。現在の候補は**勝率未確定**で、完全自律生成の統計的な最終合格を意味しない（この扱いは画面の `desc` には書かない）。手順と検証結果は `mapdesign/circulation/README.md`。

`--theme tidal` は10対10の「潮路搬送区」。既定はA–B間とC–E間の段積みコンテナ追加版 `tidal7`（370×1136m）。コンテナ追加前は `--revision tidal6`、高架変更前は `--revision tidal5`、山の追加前は `--revision tidal4`、街区追加前は `--revision tidal3`、旧710m版は `--revision tidal1`。地上中央の争奪・高所からの干渉・中央を分けた争奪の3配置を同じ工業港から生成する。青基地前は工場間・連絡橋下・10〜12mの屋根、橙拠点前は住宅の路地・庭壁・共同住宅の屋上から接近する。正面ゲートへの地上路も残す。屋根へは坂かジャンプパッドを使い、展望台にはリフトを置く。中央高架は20m高の斜め1本で、両端の坂と2基のリフトを接続する。B–C間には地上壁・橋上塔・積み荷を置く。A–B間には6群、C–E間には8群の段積みコンテナを前後左右へずらし、複数の地上路を残す。射線と実弾、上下の通行は `node tools/test/tidal_frontline_check.js dbg` で検査する。生成例は `node tools/generate_map.js --theme tidal --seed 20261020 --placement-seed 20261020 --placement-attempts 192`。両軍の再出撃と本体Botによる占拠は `node tools/test/tidal_check.js dbg`、街路・正面の実走と射線は `node tools/test/tidal_district_check.js dbg` でも検査する。設計・失敗履歴・対戦結果は [潮路搬送区の記録](../../mapdesign/tidal/README.md)。

白煙循環区の修正実験は `--revision baseline|cover1|cover2|repair3|reviewed250` で再現する（既定値 `reviewed250` は最新本体で棄却した追加配置を戻した登録版）。プラント・共通地形・昇降設備を固定し、戦場別の `barricades`・`plantPods` と経路を生成し直す。高架縦断は対照として物理データを維持する。完全に隠す要件は両端プラントのポッドへ適用し、中央ポッドの視認数も検査ログに残す。失敗した案と次の設計で使う知識は [知識台帳](../../mapdesign/LESSONS.md)へ蓄積する。

### ジャンプパッド・ジップライン・リフト（任意）

基地用の `layout` の見た目には `baseWall`（常設防壁）、`container`、`trailer`、`barracks`、`office`、`hesco`、`prefab` も指定できる。すべて通常の箱の衝突・射線判定を使う。色や建材によるダメージ倍率は無い。屋根には窓を繰り返さない。

基地守備は任意の `baseDefense: {posts:[[x,z],…], gates:[[x,z],…], yard:[x,z,幅,奥行き], gateDepth:8, leash:150, alertRadius:340, responseRadius:600, reinforcements:2}`。地点は青側を記述し橙へ点対称に展開する。`posts` は基地内の常駐地点、`gates` は標識の場所、`yard` は舗装、`leash` はレーダー侵入者を追うコアからの距離。`alertRadius` は通常索敵による接近警戒範囲（省略時は侵入情報のみ）、`responseRadius` は帰還する占拠役を選ぶコアからの距離、`reinforcements` は人数上限。地形の防壁・侵入口そのものは `layout`・`bridges` へ書く。

任意の `raidRoutes` は `[{kind:'rush'|'covert'|'radar'|'sprint', points:[[x,z,y],…], pointsR:[[x,z,y],…], objective:'core'|'radar'},…]`。攻め役へ順に割り当てる。橙の地点を省略すると青の点対称を使う。普通の武器・nav・昇降設備で通れる地点を指定し、上層地点は高さも検査する。経路ごとの任意の `pointRadius: {B:4, R:14}` は経由点の到達半径（0より大きく14m以下）。14m未満を指定した陣営では、進行方向だけで点を省略せず、指定した高さと半径まで通る。狭い足場の角で使う。省略時は従来の14mと奥行きによる省略。`botRepairRange` はBotが補給先を選ぶ距離で、省略時90m。

どれも中立の設備で、両陣営のプレイヤーとBotが同じ条件で使う。`asym: true` は全域を指定し、省略時は地形と同じ点対称で増やす。座標は nav と同じ **[x, z, 海抜y]**。高さも明記する。

```js
jumpPads: [{ at: [-20, 0, 0], rise: 28, radius: 3, exit: [-6, 0, 12] }],
ziplines: [{ from: [-111, -65, 0], to: [-102, -65, 13] }],
lifts: [{ from: [24, 0, 0], to: [16, 0, 12], size: [8, 8], speed: 5, wait: 2 }],
```

- ジップライン（v0.21、ユーザー指定「欲しいのはapexのジップライン設備なんだよな USEで上にシャーって」）：`from` と `to` の2点を結ぶ綱。低い方が乗り場で、E で掴むと 16m/s で上へ昇り、上では台の上へ押し出されて降りる。Space か E で途中で手を離せる。2点の高さの差は3m以上（build_maps が検査）。`to` は台の縁から少し外でもよい（上で台の方へ押し出す）。Botも通り道として使う。高所へ上がる設備は、まずジップラインを使う。

- ジャンプパッド：接地して踏むと真上へ射出する。`rise` は基準面からの理論上の上昇高（0超〜100m、時間刻みにより実測は少し低くなる）、`radius` は起動半径（省略時3m、2〜10m）。水平初速を加えず、射出後は通常の空中操作で移動する。`exit` はBotが着地を目指す地点で、移動の補助や瞬間移動は行わない。最高点より低く、実際に空中操作で届く床を指定し、射出方向の頭上を空ける。
- リフト：`from` と `to` の間を時間で往復する移動床（ユーザー、2026-10-20「タイマーで上がり下がりする床」としてマップの設備に残す）。垂直・斜め・水平を指定できる。`size` は床の幅・奥行き（省略時6×6m、各4〜20m）、`speed` は移動速度（省略時5m/s、0超〜30）、`wait` は両端の停止秒数（省略時2秒、0〜60）。上に立つと運ばれ、歩く・ジャンプで降りられる。乗員の頭上・進路や床の下に機体があれば停止し、空けば再開する。搭乗口と降り口、移動床の通路を空ける。
- Botは高い目標へ向かうとき、目的地に接続する設備を選び、実際に歩いて踏む・乗る。下降するリフトの下を塞がないよう乗り場の横で待つ。設備を省略したマップの目標判断は従来どおり。
- `python3 tools/build_maps.py` で型・寸法・範囲を検査し、`node tools/test/mobility_check.js dbg` で実物理とBotを検査する。配置後は実走して、パッドの上昇・横移動の時間と、リフトの乗降・頭上の空間を確認する。

白煙循環区の生成器も両設備を配置する。各高所にパッド・リフト・徒歩の迂回坂を設け、3戦場すべてに高所プラントを含める。生成時には軽量機・重量機と両陣営による全設備の乗降を実物理で検査する。`node tools/test/generated_mobility_check.js dbg` は、生成済み3戦場の高所プラントへ、本体のBot判断と経路探索でパッド・リフトから到達する検査。生成・対戦・リプレイは `mapdesign/circulation/v2/` に保存する（リプレイ・動画・大きな対戦記録はリポジトリに入れない）。

試せるマップは「昇降設備試験場 〜垂直射出と運搬〜」（`testOnly: true` なので、プレイヤーのマップ選択には出ない。試験からは `selectMap` で選ぶ）。設計と結果は `mapdesign/mobility/README.md`。施設の概要は[ユーザー指定の公式紹介](https://borderbreak.com/game/intro/facility/)を参照し、速度・寸法・外観は本作の仮置きとオリジナルモデルを使う。

### 地形の種類（`terrain` の `type`）

正の地形には任意の `keepBaseHeight: true` を指定できる。基地境界より奥でも、その地形の高さを平坦化せず残す。基地脇の山や専用の下り坂に使い、射出台・ポッド・レーダー・建屋の基礎を持ち上げないことを検査する。指定なしでは従来どおり境界から25mで高さ0へ下げる。負の地形には指定しない。

| 種類 | 項目 | 形 |
|---|---|---|
| `mesa` | x, z, r, h, slope | 頂上が平らな盛り土（頂上の半径 r、斜面の幅 slope） |
| `block` | x, z, hx, hz, h, slope | 崖で囲まれた高台（頂上の半分の大きさ hx・hz、slope は崖の幅。2.5なら登れない崖） |
| `ramp` | x0, x1, z0, z1, h | x0〜x1 の幅で、z0 の高さ h から z1 の高さ0へ下る坂（高台へ登る道） |
| `hill` | x, z, r, h | なだらかな丘（h が負ならくぼみ） |
| `trench` | x, z0, z1, w, slope, h（負） | z0〜z1 に伸びる谷やくぼ地（底の半分の幅 w、斜面の幅 slope） |

- 高い物は重ねると高い方、低い物（h が負）は足し合わせる。
- 傾き1.1（約48°）を超える斜面は登れない壁になる。ジャンプは約4.3m、滞空を使ってもそれ以上の崖は越えにくい。
- 種類を足すのはエンジン側の仕事（index.html の `featureH`）。
- 平らな所のゆるい起伏は `python3 tools/gen_rough.py <id> [--seed N]` が `hill` を並べて、terrain の「起伏ここから」〜「起伏ここまで」に書く（手で直さず作り直す）。プラントの占拠範囲・ポッド・カタパルトの台・橋・水面・石壁と家の周り・`paved` に書いた道路や広場と、もとの地形の上には置かない。

### 橋・水面・建物・Botの通り道・配置違い（v0.10.3から）

- **橋 `bridges`**：地面に埋めない板。上面に立てて、下は頭（機体の高さ4m）が板の底（上面 − 厚さ）より低ければくぐれる。弾と視線は板に当たる。点対称に足される。川に架けるなら、川底から板の底まで5m以上空ける（丘の市街地は深さ6mの川に上面0・厚さ1）。
- **橋脚**は普通の `layout` の箱（例 `[47, 12, 3, 5, 12, 'wall']`）で書いてよい（v0.10.4 から `clearPath` が高さを見て、歩く高さより0.6m以上高い箱だけを壁とみなす）。丘の市街地の橋脚は v0.10.3 の時の書き方（厚さ12mの橋）のままで、これも動く。
- **水面 `water`**：見た目だけで当たり判定は無い。地面より低い所だけ見えるので、川より大きめに張ってよい。
- **建物の見た目**：`layout` の6番目に `'house'`（切妻屋根・窓）、`'wall'`（石壁）、`'tower'`（石の塔と胸壁）。当たり判定は箱のまま（屋根は見た目だけ）。
- **Botの通り道 `nav`**：自軍側の半分の節点 `[x, z]`（橋の床の上の節点は歩く高さを足して `[x, z, y]`。例 水道橋の上なら `[60, 12, 14]`。省くと地面の高さ。橋の下の節点には書かない）と、つなぐ組 `[i, j]` を書く。`'~3'` は3番の点対称の節点。原点 (0, 0) の節点は1つだけになる（プラントの柱があるので原点には置かない）。Botは目標までまっすぐ歩けないときだけ通り道を使う。節点は曲がり角・橋の両端・坂の上下・プラントの手前に置き、つなぐ節点どうしは障害物も登れない段差もなくまっすぐ歩けるようにする（map_check の6で★が出なくなるまで直す）。点対称の節点どうしを結ぶ線は必ず原点を通るので、柱にぶつからない別の組でつなぐ。
- **配置違い `variants`**：地形と `layout` はそのままで、書いた項目（`plants`・`plantPods`・`catapults` など）だけ差し替えた版がマップ選択に「名前 〜name〜」（ID は `<id>-<キー>`）で並ぶ。

## 守ってほしい決まり（ユーザーが決めたもの）

- いちばん自軍側・敵軍側のプラントのリペアポッドは、プラントの後ろ（自軍ベース側）の土手と窪地に置き、敵陣側から見えないようにする（v0.9.2）。形は台地演習場のAが見本（`block` 2つと `trench` 1つ）。
- プラントからの再出撃は、プラントの中心から自軍ベース側へ46〜52m離れた所（エンジンが決める）。その場所が崖の上や障害物の中にならないようにする。
- ベースのカタパルトは各ベースに左右2基ずつ（v0.9.2）。カタパルトはどの陣営の物でもなく、敵の台も誰でも使える（v0.10.5、ユーザー指定）。台のすぐ前（飛ぶ向き4.5m・8m）に砲身の輪が立つので、そこに家などを置かない。
- レーダーは各ベースの左奥（v0.9.3）。コアの傘はエンジンが付ける。
- 公式のマップ名・地名は使わない。
- 10対10用のマップは試合10分、5対5は5分にしている（Claudeの判断、元のゲームに合わせた）。

## 確かめ方

```
python3 tools/build_maps.py
python3 tools/test/make_dbg.py /tmp/mapcheck
node tools/test/map_check.js /tmp/mapcheck <id>          # 全部（カタパルトとスクリーンショットつき）
node tools/test/map_check.js /tmp/mapcheck <id> --quick  # 施設・ポッドの見え方・再出撃位置だけ
```

`map_check.js` は Playwright と Chromium（swiftshader）で動き、次を文で出す。良し悪しは読む人が決める。
1. 施設の地面の高さと、障害物に埋まっていないか（★が付いたら直す）
2. 自軍側の半分のプラントのポッドが、そのプラントの中心より敵ベース寄りの15m格子（180m以内、目の高さ4.6m）の何か所から見えるか。隠したいポッドは0か所にする
3. 各プラントからの再出撃位置（中心からの距離と z）
4. 自軍側のカタパルトの着地点と、書いた着地点との差（6mより大きいと★）
5. 自軍ベースと、各プラントの再出撃位置あたり（中心から自軍ベース側へ48m）から前を見たスクリーンショット（作業フォルダに `map_<id>_*.png`）
6. Botの通り道（`nav` があるとき）：まっすぐ歩けないリンク、障害物の中の節点、つながっていない節点、プラントやカタパルトを見通せる節点が近くに無い所に★

上から見た図（高さ・登れない斜面・障害物・橋・通り道・再出撃位置）は `python3 mapdesign/map_top.py <id> 出力.png` で数秒で出せる（ブラウザ不要）。

Bot同士の対戦（プラントの取り合いが起きるか、Botが詰まらないか）はまだ道具にしていない。必要ならエンジン側のスレッドに頼む。

## 公開

- 試作の公開ページは1つ（https://claude.ai/artifact/EBViVFVaYZFHUNuuF3bBPF）。公開ページの `maps.js` を出すのは**マップ製作のスレッドだけ**（2026-10-18、エンジン側と取り決め）。エンジン側は公開の `files` に maps.js を入れない（入れなかったファイルは公開ページに残る）。
- マップ製作側の公開：公開ページを読んでそのページ（index.html）をそのまま出し、`files` に `maps.js` だけを入れる（`files` の元は自分の scratchpad へコピーしてから渡す）。sounds.js・music.js は入れなければ公開ページの物が残る。
- ディスクの `maps.js` は `build_maps.py` が通るたびに作り直されるので、作りかけのマップが入ることがある。公開してよいマップだけが入っている時に公開する。
- 公開の `label` は、マップだけの変更なら「マップ：〇〇」とする。
- 配布zipはエンジン側が作る：公開ページの maps.js を取ってきて `python3 tools/build_zip.py <版> --maps <そのファイル>`（`--maps` なしならディスクの maps.js をそのまま入れる。build_zip.py は maps.js を作り直さない）。版の番号はエンジン側が付ける。マップだけの配布は `<今の版>-map<n>`（例 0.10.1-map1）とし、次のエンジンの版に取り込む。
